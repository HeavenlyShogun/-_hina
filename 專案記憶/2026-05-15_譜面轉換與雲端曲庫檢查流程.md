## 譜面系統出錯時的檢查順序

1. 先跑 `npm run build`。
   - 若在沙盒或 Windows 權限環境出現 `spawn EPERM`，改用非沙盒環境重跑，這通常是 Vite realpath 權限問題，不代表程式碼壞掉。
   - 若出現 JSX、import、JSON parse 錯誤，先處理對應檔案，不要先懷疑譜面內容。

2. 跑 `npm run scores:stress`。
   - 正常狀態會列出 Slim JSON 檔名、bytes、events、noteEvents、avgMs、p95Ms、maxMs。
   - 若出現 `No score files matched`，代表測試腳本指向舊資料夾或曲庫資料夾不存在。
   - 若單一檔案 JSON parse 失敗，先檢查該 Slim JSON 是否被截斷或不是合法 JSON。

3. 檢查目前曲庫入口。
   - 正式曲庫入口應該是 `src/data/importableScoreFiles.js`。
   - `src/data/featuredScores.js` 只應轉接 Slim 曲庫，不應重新 import `src/data/scores/*-midi.json`。
   - 若 bundle 重新出現 600 KB 以上的譜面 chunk，優先搜尋 `src/data/scores`、`*-midi.json`、`不可匯入太大譜面` 是否被 import。

4. 檢查播放解析路徑。
   - Slim Score 走 `src/utils/score.js` 的 `version === '3.2-ultra-slim'` 分支。
   - V3 event stream 走 `version === '3.0'` 分支。
   - V2 `tracks/events` 仍是相容分支，不應作為新譜面的主要格式。

5. 檢查轉換器。
   - MusicXML 前端轉換走 `src/utils/musicXmlToSlim.js`，輸出 `3.2-ultra-slim`。
   - MIDI 前端匯入目前仍走 `src/utils/midiToV2.js`，這是相容路徑；正式產線仍應優先用 Slim 產線。

6. 檢查雲端儲存內容。
   - JSON 譜面儲存後，Firestore 的完整譜面文件必須有可解析的 `rawText` 或 `content` 字串。
   - 若摘要列表存在但讀取後無法播放，優先檢查 `src/services/firebase.js` 的 `createScoreDocumentData` 是否有把 JSON content 序列化保存。

## 雲端曲庫的定位

- 目前 Firebase 雲端曲庫主要是「使用者曲庫同步」與「摘要列表管理」，不是大檔案 CDN。
- Firestore 單文件大小有限制，肥版 V2 JSON 接近或可能超過實務安全範圍；大型譜面應先轉成 Slim JSON，再儲存或部署。
- 目前程式以約 850 KB 作為 Firestore 譜面文件安全門檻，超過就阻擋儲存並提示轉換。
- 若目標是降低網頁初始檔案大小，優先做法是：
  - 不要在前端靜態 import 肥版 V2 JSON。
  - 使用 Slim JSON 動態載入。
  - 未來若要真正雲端取譜，應考慮 Firebase Storage 或 Hosting 靜態 JSON，再由 Firestore 只保存 metadata / URL。
