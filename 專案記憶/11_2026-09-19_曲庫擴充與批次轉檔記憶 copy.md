## 轉檔產線使用方式

日後只要把 `.mid` 放進：

```text
風物之琴譜/縮小版可匯入譜面/midi/
```

再執行：

```bash
cmd /c npm run scores:slim:library
```

腳本會輸出到：

```text
風物之琴譜/縮小版可匯入譜面/slim-json/
```

若需要覆寫既有 slim JSON：

```bash
cmd /c npm run scores:slim:library -- --force
```

## 雲端或後端曲庫建立方向

目前設計已經有很好的基礎：local slim JSON 使用 `import.meta.glob` lazy load，Firestore 則負責使用者個人譜面與公開分享。曲庫量繼續成長時，建議把「內建曲庫」從 app bundle 中逐步抽離為雲端索引 + 靜態譜面檔。

推薦方向：

- Firebase Storage 或 Hosting 存放 slim JSON 檔案：`score-library/slim-json/<slug>-slim.json`。
- Firestore 只存 metadata index，不直接塞完整譜面：`artifacts/{appId}/scoreLibrary/{scoreId}`。
- metadata 欄位包含 `id`、`title`、`slug`、`artist`、`sourceType`、`storageFormat`、`bpm`、`noteCount`、`trackCount`、`durationTicks`、`bytes`、`tags`、`difficulty`、`localeTitle`、`storagePath`、`downloadUrl`、`updatedAt`。
- App 啟動時先載入索引，使用者點選曲目時才下載 slim JSON；這能避免每次 build 都把全部曲目切成前端 chunks。
- 保留現在的 local slim JSON 作為「離線核心曲庫」與開發 fallback，雲端曲庫作為可擴充來源。
- 加一個 manifest 檔：`public/score-library-manifest.json` 或 Firestore query cache，用來提供搜尋、分類、版本號與增量更新。
- 之後可新增後端匯入流程：上傳 MIDI/MusicXML -> Cloud Function 或本機 CI 轉 slim JSON -> 寫入 Storage -> 更新 Firestore metadata。

## 錦上添花設計方向

- 曲庫 UI 加上分頁或虛擬清單，避免大量曲目時一次渲染太多項目。
- 新增篩選：來源格式、BPM 區間、長度、難度、語系、標籤、最近新增。
- 曲目卡保留現在的美術調性，但 metadata 更精準：音符數、軌道數、估計長度、檔案大小。
- 新增「雲端可用 / 本地已快取」狀態，搭配 IndexedDB 快取已載入的 slim JSON。
- 批次轉檔腳本未來可再輸出 `score-library-manifest.json`，讓本地與雲端曲庫共用同一份索引結構。
