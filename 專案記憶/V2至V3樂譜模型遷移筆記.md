
# V2 至 V3 樂譜模型遷移筆記

## 2026-05-08

### 背景

目前專案在處理較長或較複雜的樂譜時，前端互動（特別是播放時的 UI 更新）會出現明顯的卡頓與延遲。經分析，根本原因在於目前使用的 **第二版 (V2) 樂譜資料結構** 及其處理方式的效能瓶頸。

### 問題分析：V2 模型的效能缺陷

V2 模型的核心是一個「音符列表」，其中每個音符都是一個包含 `startTick`（開始時間）和 `durationTicks`（持續時間）的物件。例如：

```json
{
  "version": "2.0",
  "notes": [
    { "note": 60, "startTick": 0, "durationTicks": 100 },
    { "note": 62, "startTick": 50, "durationTicks": 150 },
    // ... 更多音符
  ]
}
```

這種結構的致命缺點在於，當播放指標 (playhead) 移動到任何一個時間點 `T` 時，為了判斷哪些音符應該被點亮（即「正在發聲」），播放控制器必須 **遍歷整個 `notes` 陣列**。對於每一個音符，它都需要進行一次區間判斷：`T >= note.startTick && T < (note.startTick + note.durationTicks)`。

當樂譜包含成千上萬個音符時（即使用者所說的 "token 太多"），這個遍歷和判斷的計算量會變得極為龐大，導致瀏覽器主執行緒被長時間阻塞，從而引發畫面凍結和卡頓。

### 解決方案：遷移至 V3 事件流模型

為了解決此效能問題，我們決定將核心資料模型遷移至您先前在 `專案記憶/第三版.md` 中定義的 **第三版 (V3) Tick 動態事件清單** 模型。

V3 模型的核心思想是將樂譜從「狀態列表」轉變為「事件流」。我們不再儲存每個音符的開始與結束狀態，而是將它們拆解為兩個獨立的、帶有精確時間戳的事件：`note_on` 和 `note_off`。所有事件會被預先排序。

```json
{
  "version": "3.0",
  "events": [
    { "tick": 0, "type": "note_on", "note": 60 },
    { "tick": 50, "type": "note_on", "note": 62 },
    { "tick": 100, "type": "note_off", "note": 60 },
    { "tick": 200, "type": "note_off", "note": 62 },
    // ... 更多按 tick 排序的事件
  ]
}
```

**V3 模型的優勢：**

*   **O(1) 等級的查詢效率：** 播放器不再需要遍歷整個樂譜。由於事件已經按 `tick` 排序，播放控制器只需要維護一個指向當前事件的指標。當播放指標前進時，它只需處理那些 `tick` 值與當前時間完全匹配的事件即可。這將尋找當前活動音符的計算複雜度從 `O(N)` 大幅降低到接近 `O(1)`。
*   **簡化播放邏輯：** 播放器的狀態管理變得更簡單。它不再需要自己計算音符的結束時間，只需被動地回應 `note_on` 和 `note_off` 事件，並更新當前發聲的音符集合即可。

### 實施步驟

1.  **建立轉換工具 (`scoreV2toV3.js`)**
    *   我已經在 `src/utils/scoreV2toV3.js` 中建立了一個公用函式 `convertV2toV3`。
    *   此函式負責接收一個 V2 格式的樂譜物件，遍歷其 `notes` 陣列，為每個音符產生對應的 `note_on` 和 `note_off` 事件，並將這些事件按 `tick` 排序，最後輸出一份完整的 V3 樂譜物件。

2.  **產生 V3 參考範例 (`v3_event_stream_example.js`)**
    *   為了給後續的前端重構提供一個清晰、具體的開發目標，我使用 `convertV2toV3` 工具將現有的 `combined-4-midi.json` 轉換為 V3 格式。
    *   轉換結果已儲存於 `專案記憶/v3_event_stream_example.js`。開發團隊可以參考此檔案的結構來調整播放器及 UI 元件的邏輯。

### 後續計畫

接下來的開發工作將圍繞 V3 模型展開：

*   **重構播放引擎：** 修改 `useScorePlayback.js` 和 `playbackController.js`，讓它們能夠直接消費 V3 事件流，而不是 V2 的音符陣列。
*   **更新 UI 元件：** 調整 `SheetDisplay.jsx`、`PianoKeys.jsx` 等與音符狀態相關的 UI 元件，使其能夠響應來自新播放引擎的事件，高效地更新畫面。
*   **資料流整合：** 確保從 `firebase.js` 或 `importableScoreFiles.js` 載入的樂譜資料，在進入播放流程前，都能被 `convertV2toV3` 工具正確轉換。

這次遷移是解決網站卡頓問題、提升使用者體驗的關鍵一步。現有 V2 邏輯將被保留作為相容層，但所有新功能和效能優化都將基於 V3 模型進行。
