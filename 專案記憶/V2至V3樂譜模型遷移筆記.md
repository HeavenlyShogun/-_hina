# V2 至 V3 樂譜模型遷移筆記

更新日期：2026-05-11

## 結論

V3 事件流已可正常支撐目前的播放邏輯，最新版彈奏邏輯已達到可穩定、完整播放譜面的狀態。現階段的主要瓶頸不再是播放正確性，而是譜面資料量過大造成的載入、解析、渲染與互動卡頓。

## 目前狀態

- 播放邏輯：
  - 已可穩定播放大型 MIDI 轉入譜面
  - `play / pause / resume / seek` 已可正常運作
  - JSON / 事件流譜面可直接進入目前播放鏈
- 譜面來源：
  - 專案目前主要保留兩份譜面：
    - `surges`
    - `neo-aspect`
- 目前設定：
  - `neo-aspect` 預設 BPM 已改為 `180`
- 目前問題：
  - 譜面檔案過大
  - JSON 結構繁雜
  - 前端載入與編輯預覽成本高
  - 網頁卡頓主因已明確指向大譜面資料本身

## 目前性能判斷

現有卡頓主要不是音訊 scheduler 邏輯錯誤，而是以下幾項疊加：

- 單一譜面 JSON 體積大
- `tracks.events` 數量過多
- 載入後還要做前端正規化與結構整理
- 預覽、時間軸、編輯器、區段資訊同時依賴大型資料
- import 後保留過多視覺與 metadata 資訊

## 下次工作重點

下次作業不要再把重心放在「播放邏輯修正」，而是放在「譜面穩定輸出與輕量化」。

### 第一優先

- 建立穩定的譜面輸出格式
- 明確定義保留欄位與可刪欄位
- 確保輸出後仍可完整播放

### 第二優先

- 精簡譜面內容
- 減少不必要 metadata
- 減少不必要 visual mapping 附帶資訊
- 減少重複欄位
- 必要時改成更輕的播放輸入格式

### 第三優先

- 對大型譜面做播放前預處理
- 將 UI 顯示用資料與播放用資料拆開
- 避免編輯器與預覽直接持有完整重物件

## 建議的優化方向

### 1. 區分播放版與編輯版譜面

- 播放版：
  - 只保留播放必要欄位
  - 例如 `tick`、`durationTicks`、`key`、`velocity`、必要 `transport`
- 編輯版：
  - 保留完整 metadata、來源資訊、參考資訊

### 2. 產生精簡輸出

- 對 MIDI 匯入結果新增一個 slim/export 階段
- 專門輸出給前端播放使用
- 避免前端每次都吃完整原始轉譜結果

### 3. 降低 UI 綁定成本

- 大譜面不要直接全文塞進編輯器
- 大譜面預覽只顯示摘要
- 播放時避免重建過多衍生資料

### 4. 先處理 `surges`

- `surges` 是目前最能暴露性能問題的樣本
- 下次應優先拿它做精簡輸出實驗與壓力測試

## 下次接手時的任務描述

可以直接視為：

1. 不再修播放正確性，因為目前版本已可正常彈奏。
2. 專注在大型譜面穩定輸出。
3. 專注在精簡與優化譜面資料。
4. 目標是降低卡頓，而不是再增加更多譜面功能。
